# R2 Mixed-Patch Policy (R2-12)

**Status: design only.**

## Invariant

> A Forge process serves game data from exactly one `CanonicalDataManifest`. Every family consumed as TRUSTED or ADVISORY carries the manifest's SourceIdentity (game version, build, GameAssembly sha256) and the manifest's `snapshot_id`. Anything else is rejected at load time.

The audit observed these combinations in production today:
- 1.4.6 v2 bundles beside pre-1.4.6 `data/` stamped `unknown` (SYS-3);
- `/api/version` hard-coding 1.4.3 / season 4 (DRIFT-3);
- builds defaulting to patch 1.2.1 (DB-3);
- hand-authored constants (EXT-3, DOC-11).

Under this policy, none of those can be served together as one dataset.

## Rules

| # | Rule | Enforced by | Failure |
| --- | --- | --- | --- |
| M1 | Exactly one active `data_version` (`data/canonical/CURRENT`) per process; read once at startup | `CanonicalDataStore` (R2-P02) | Process refuses to serve game data (`503 DATASET_UNAVAILABLE`) |
| M2 | Every family's `_meta` identity (patch, build, GameAssembly sha256 where present, and for trees the decoder build stamp) equals the manifest SourceIdentity | Loader check L7 | `MIXED_PATCH` |
| M3 | Every family's content hash equals the run manifest of the same `snapshot_id` | Loader check L5 | `CONTENT_HASH_MISMATCH` |
| M4 | Game-data registries can only be constructed from `CanonicalDataStore`. A registry constructor that receives a path, dict or legacy loader raises. | Registry factories (R2-P03), static test T11 | `FOREIGN_SOURCE` |
| M5 | Hand-authored constants that encode game facts must be declared either `FORGE_RULE` (owned by the Forge, documented, versioned with the code) or replaced by canonical data. Each must carry `valid_for_data_versions` or `game_independent: true`. | Constants registry (R2-P12), test T11 | Startup refuses an undeclared game-fact constant once R2-P12 lands |
| M6 | API responses carrying game data include `data_version` and per-family `trust` | Response envelope (R2-P09) | Contract test T7 |
| M7 | Frontend artifacts embed the `data_version` they were built from; the frontend refuses to combine API data with an artifact of a different `data_version` | R2_FRONTEND_AUTHORITY_PLAN.md, test T8 | Frontend shows `DATASET_MISMATCH`; never renders mixed data |
| M8 | A saved build records the `data_version` that interpreted it; loading it under a different `data_version` runs the declared compatibility path, never silent reinterpretation | R2_DATABASE_PROVENANCE_PLAN.md | Build marked `REQUIRES_REVALIDATION` |

## Explicitly compatible manifests

A dataset may legitimately span artifacts produced at different times. For example:
- canonical affixes regenerated after an extractor fix, from the same snapshot;
- a later R1 run of the same build.

Both are allowed only through an explicit compatibility declaration:

```json
"compatibility": {
  "mode": "SAME_SNAPSHOT_REBUILD",
  "snapshot_id": "<same>",
  "families_rebuilt": ["affixes"],
  "rebuild_run_manifests": ["snapshots/runs/<id>.rebuild-1.json"]
}
```

Allowed modes:

| Mode | Meaning | Allowed |
| --- | --- | --- |
| `SINGLE_SNAPSHOT` | Every family from one run manifest | Yes (default) |
| `SAME_SNAPSHOT_REBUILD` | Same `snapshot_id` and SourceIdentity; some families regenerated by a newer extractor commit, each with its own run manifest | Yes |
| `CROSS_BUILD` | Families from different game builds | **No.** There is no mechanism that makes two builds' data one trusted dataset. |

## Hand-authored and third-party inputs

| Input class | Examples (from R1 consumption inventory and audit) | R2 treatment |
| --- | --- | --- |
| Hand-curated game data | `data/items/base_items.json`, `backend/app/game_data/classes.json`, `constants.json`, `skills.json`, `data/items/crafting_rules.json`, `data/entities/enemy_profiles.json` | Replaced by canonical typed views where the game has the data. Otherwise declared `FORGE_RULE` with a documented basis, and never labelled extracted. |
| Patch-tied magic numbers (DRIFT-7) | `BASE_TYPE_ID_TO_ITEM_TYPE_ID.ts` (stops at 33), `MAX_PASSIVE_POINTS = 113`, pinned build numbers | Derived from the canonical dataset at load or build time; deleted as constants |
| Third-party data | community skill trees (`data/classes/community_skill_trees.json`), LE Tools IDs | Never part of the trusted dataset. Importer mapping tables are versioned against a `data_version` (R2_IDENTITY_POLICY.md). |

## Upgrade procedure (new patch)

1. The R1 operator run produces a snapshot, a run manifest and a certification.
2. `import_canonical_bundle.py` creates `data/canonical/<new data_version>/` (L1–L11 checked offline).
3. The CI contract suite (R2_CONTRACT_TEST_PLAN.md) runs against the new bundle, including the build-revalidation report for persisted builds (sample from fixtures).
4. A single commit switches `CURRENT` and regenerates frontend artifacts from the same bundle (M7).
5. Deploy. The old bundle directory stays until no persisted build references it in `REQUIRES_REVALIDATION`, then it is archived.

Rollback means switching `CURRENT` back. Bundles are immutable, so rollback is exact.
