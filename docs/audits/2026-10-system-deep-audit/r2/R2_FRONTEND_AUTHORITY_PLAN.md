## Decision: one bundle, two delivery channels, one identity

| Data | Channel | Why |
| --- | --- | --- |
| Tree graphs:<ul><li>passive, skill and weaver nodes and edges;</li><li>mastery grouping;</li><li>tree ↔ ability;</li><li>layout overlay.</li></ul> | **Build-time artifact** generated from `data/canonical/<data_version>/` by one generator (`scripts/build_frontend_data.py`, R2-P10) into `frontend/src/generated/canonical/<data_version>/*.json` + `index.ts` | Large, static per dataset, needed offline by the planner. The static host (Render static site, nginx) serves it without the API. |
| Reference catalogues:<ul><li>affixes;</li><li>items and subtypes;</li><li>uniques and sets;</li><li>blessings;</li><li>classes and masteries;</li><li>property names.</li></ul> | **API** (`/api/ref/*`, R2-P09) from `CanonicalDataStore` | Already API-delivered for items. Filtered queries. One server-side authority with trust labels. |
| Calculations | API only | The frontend stops computing game math from hand tables (`simulation.ts`, `useLiveStats.ts`). Where a client-side preview remains, it consumes the API's numbers. Calculation semantics are R6. |

Both channels carry the **same `data_version`**:

- **Generated artifact:** it exports `DATA_VERSION` and `CONTENT_SHA256`. The hash is the canonical content hash of the bundle families it was generated from, taken from `CANONICAL_DATA_MANIFEST.json`.
- **API:** every API response carries `data_version` (R2_MIXED_PATCH_POLICY.md M6).
- **Startup check:** at startup the frontend compares its artifact `DATA_VERSION` with `/api/version.data_version`.
  - **Match:** proceed.
  - **Mismatch:** the planner shows `DATASET_MISMATCH` ("This page was built for data X; the server serves Y. Reload.") and renders no tree. Mixed data is never rendered.
  - **API unreachable:** explicit "version unavailable". No hard-coded patch.

## Generator contract (R2-P10)

`scripts/build_frontend_data.py --bundle data/canonical/CURRENT`:

1. **Reads only the bundle.** It never reads `data/` legacy files, `exports_json`, or `frontend/src/data/raw/*`; the layout overlay is the exception, see below.
2. **Emits typed JSON:**
   - per passive tree: `{class_id, tree_id, nodes[{node_id, max_points, mastery_index, name_key, stats_ref}], edges[{from, to, points_required, resolution}], masteries[{index, name, localization_key}]}`;
   - per skill tree: `{tree_id, ability_id, nodes[...], edges[...]}`;
   - integrity and trust per tree.
3. **Writes the version module.** It writes `index.ts` exporting `DATA_VERSION`, `CONTENT_SHA256` and typed accessors keyed by `(class_id, node_id)`, `(tree_id, node_id)` and `ability_id`. No name keys.
4. **Is deterministic:** sorted keys, no timestamps. Running it twice gives identical bytes.
5. **Is CI-checked:** the job regenerates the artifact and fails on diff. A stale or hand-edited artifact cannot merge.

### Layout overlay (presentation only)

Canonical trees carry no coordinates. Node positions are RectTransform data on the node GameObjects, which the R1 MonoBehaviour TypeTree dump does not include.

- **Overlay:** until an extractor adds it, x/y/icon come from a declared presentation overlay keyed by `(tree_id, node_id)`: `frontend/src/generated/layout/<data_version>.json`, built from the existing third-party layout.
- **Rules:**
  - the overlay may only position and decorate existing canonical nodes;
  - its node-id set must equal the canonical node set (parity test);
  - extra or missing ids fail the build;
  - nodes without a position are drawn in an explicit "unplaced" area, never at 0,0 (FB-1103);
  - the overlay carries its own provenance (`source: lastepochtools layout <version>`) and is never used for identity, edges or stats.
- **Optional extractor work:** adding RectTransform positions to the R1 tree-node contract, presentation-only (R2-P04 optional scope), would remove the third-party dependency.

## Parity test (T8)

The CI job `r2-parity`:
1. starts the API on the committed bundle;
2. dumps `/api/ref/*` and the tree endpoints;
3. builds the frontend artifact;
4. asserts:
   - identical `data_version` and content hash;
   - for every tree: equal node sets, edge sets (including `points_required`), mastery grouping and tree ↔ ability links;
   - for affixes and items: equal id sets and ranges;
   - layout overlay node set equals the canonical node set.

Any difference fails the merge. There is no manual duplicate to maintain: the frontend holds no hand-written game facts after R2-P10.
